# Calendly MCP 测试用例生成知识库

> 用途：作为 AITC 知识库检索语料，辅助针对「Dealclaw × Calendly MCP」预约管理场景生成高质量测试用例。
> 本文档由《Calendly 需求文档.docx》与《Calendly_MCP_测试用例.xlsx》（26 条用例）提炼而成，覆盖领域上下文、全局业务规则、非功能质量属性与分模块测试知识。检索时建议以「模块名 + 测试意图」为查询，例如「预约创建 冲突 备选」「取消 提醒联动」。

## 1. 系统概述与用户角色

Dealclaw 集成 Calendly MCP（AI 代理服务），使商家/客户可在 WhatsApp 聊天中以自然语言完成预约管理，无需进入 Calendly 页面。业务闭环为：授权连接 → 预约创建 → 自动提醒 → 改期/取消 → 异常处理。

四类角色及其交互界面：
- 客户（最终用户）：通过 WhatsApp 聊天窗口交互，免登录完成预约。
- 商家（服务提供方）：通过 Dealclaw Web 后台管理预约与授权。
- BA（前端对话代理）：负责意图识别、引导、话术生成，嵌入 WhatsApp 与 Dealclaw。
- SA（后台调度代理）：负责调用 Calendly API、触发定时任务，运行于系统内部。

生成用例时务必区分「谁在操作、通过什么界面」：客户经 WhatsApp 自然语言输入，商家经 Web 后台指令，SA 由系统内部调度。

## 2. 全局业务规则（硬约束）

以下规则对全部模块生效，生成用例时必须作为前置假设或断言依据：
- 营业时间：每日 09:00–18:00，非营业时间禁止创建/改期预约。
- 提醒时机：会议开始前 30 分钟发送提醒，固定值不可配置。
- 改期确认超时：发起改期后 24 小时未回复，触发 Follow-up 并通知商家。
- 唯一性约束：同一身份（客户）+ 同一开始时间，全局唯一，禁止双预约（幂等）。
- 邮箱必填：调用 Calendly 创建 API 前，必须已收集到客户邮箱，否则不得发起创建。

## 3. 非功能需求与质量属性

生成用例时，除功能场景外必须覆盖以下质量属性：
- 服务容错：当 Calendly MCP 不可用时，必须返回标准话术，严禁向用户暴露堆栈、严禁伪造成功结果。
- 并发安全：高并发下必须杜绝「双预约」，唯一性约束需靠服务端校验而非前端。
- 消息解析鲁棒性：用户输入含乱码、截断时，应有兜底引导话术而非崩溃。
- 多语言：葡萄牙语（巴西）为首选语言，用例需覆盖葡语输入与回复。

## 4. 测试设计约定

- 优先级定义：P0=核心主流程（Demo 必跑）；P1=主要场景；P2=边界/异常；P3=低频/长尾。
- 用例字段约定：用例ID、模块、用例名称、优先级、前置条件、测试步骤、测试消息输入、预期结果。
- 自然语言输入测试要点：消息含模糊时间、错别字、多意图、跨语种混合时，系统应追问或优雅降级，而非失败。
- 三态确认模式：创建前收邮箱、取消二次确认、改期需确认——此类写操作必须验证「确认」与「反悔/超时」双向分支。
- 定时任务联动：任何会导致预约消失的操作（取消、改期），必须验证对应提醒任务被移除。

## 5. 分模块测试知识

### 5.1 模块：OAuth 授权连接

#### 需求要点
客户/商家通过 OAuth 连接 Calendly；Token 过期或被撤销时系统自动检测，给出友好提示与重新授权链接，严禁直接报错；用户拒绝授权时授权状态保持不变并回复「授权未完成」。

#### 关键业务规则
授权是后续所有操作的前置条件；Token 失效需可恢复而非阻断；拒绝授权不改变既有状态。

#### 已有测试场景
- AUTH-01 正常授权连接（P0，主流程）
- AUTH-02 Token 过期后引导重新授权（P1）
- AUTH-03 用户拒绝授权后的状态保持（P2）

#### 生成建议（补充覆盖点）
- 授权中途网络中断的恢复路径；
- 多账号/多商家绑定隔离；
- 授权成功后首条预约的引导话术；
- Token 临近过期时的提前刷新策略。

### 5.2 模块：预约创建

#### 需求要点
正常创建需「查闲档→建事件→发确认」；时段冲突时推荐 2–3 个备选；模糊时间需追问澄清；非营业时间（9–18 外）拦截并推荐营业时段；过去时间拦截；同一客户同开始时间重复创建需防重；创建前强制收集邮箱。

#### 关键业务规则
营业时间 9–18；邮箱必填且须在调用 API 前收集；相同身份+开始时间唯一。

#### 已有测试场景
- BOOK-01 有空档正常创建（P0）
- BOOK-02 时段占用推荐备选（P1）
- BOOK-03 模糊时间追问（P2）
- BOOK-04 超营业时间拦截（P2）
- BOOK-05 过去时间拦截（P2）
- BOOK-06 重复创建防重（P2）
- BOOK-07 创建前收集邮箱校验（P1）

#### 生成建议（补充覆盖点）
- 跨时区时间解析的正确性；
- 邮箱格式非法时的校验话术；
- 连续多次冲突时备选推荐数量上限（2–3 个）；
- 创建成功后的确认消息内容完整性（时间/主题/会议链接）；
- 闲档查询失败时的降级处理。

### 5.3 模块：改期（Reschedule）

#### 需求要点
客户主动改期需「删旧+建新」一步完成；商家发起改期由 SA 查空档后发客户确认；客户反建议时间转商家人工确认；超时 24h 未回复触发 Follow-up 并通知商家。

#### 关键业务规则
改期确认超时 24h；客户主动改期原子化（删旧建新同一步）；商家发起需客户确认。

#### 已有测试场景
- RESCHED-01 客户主动改期（P0）
- RESCHED-02 商家发起改期（P1）
- RESCHED-03 客户反建议转人工（P2）
- RESCHED-04 超时未回复触发 Follow-up（P3）

#### 生成建议（补充覆盖点）
- 改期后原提醒任务清理与新建提醒的正确性；
- 改期冲突时的备选推荐；
- 商家改期完成后商家收到完成通知的闭环；
- 改期到非营业时间的拦截。

### 5.4 模块：取消（Cancel）

#### 需求要点
取消需二次确认；取消不存在的预约时友好告知而非报错；确认前反悔则保留原预约。

#### 关键业务规则
取消为写操作，需二次确认；取消对象不存在时不得报错。

#### 已有测试场景
- CANCEL-01 主动取消（P0）
- CANCEL-02 取消不存在的预约（P2）
- CANCEL-03 取消前反悔保留（P2）

#### 生成建议（补充覆盖点）
- 取消后对应提醒任务被移除（与提醒模块联动）；
- 批量/重复取消的幂等性；
- 取消确认消息的明确性（时间/主题）。

### 5.5 模块：日程查询

#### 需求要点
支持周视图（按日期排列，含客户名/主题）；单日查询不混入其他日期结果。

#### 关键业务规则
周视图按日期聚合；单日查询结果严格限定在目标日期。

#### 已有测试场景
- SCHEDULE-01 查询下周日程（P1）
- SCHEDULE-02 查询特定日（P2）

#### 生成建议（补充覆盖点）
- 空日程的友好返回；
- 跨周/跨月边界日期的正确性；
- 多客户预约的区分展示；
- 查询与取消/改期后的数据一致性。

### 5.6 模块：会议提醒

#### 需求要点
会前 30 分钟提醒；客户侧经 WhatsApp、商家侧经内部消息；取消后必须移除对应提醒任务。

#### 关键业务规则
提醒固定会前 30 分钟；取消/改期必须联动提醒任务生命周期。

#### 已有测试场景
- REMIND-01 提醒客户（P1）
- REMIND-02 提醒商家（P1）
- REMIND-03 取消后不再提醒（P1）

#### 生成建议（补充覆盖点）
- 提醒时间精确性（±误差容忍）；
- 改期后提醒时间随新时间更新；
- 提醒发送失败的重试机制；
- 多提醒（同一客户多场会议）的隔离。

### 5.7 模块：异常处理（非功能）

#### 需求要点
覆盖 MCP 服务不可用、并发双预约、无效/乱码消息、多语言（葡语）四类异常，均要求优雅降级而非崩溃或暴露内部错误。

#### 关键业务规则
外部依赖故障时返回可控话术；不暴露内部错误；不伪造成功；并发靠服务端唯一性约束防护。

#### 已有测试场景
- ERR-01 服务不可用标准话术（P2）
- ERR-02 并发双预约防护（P2）
- ERR-03 无效消息兜底引导（P2）
- ERR-04 葡语多语言（P1）

#### 生成建议（补充覆盖点）
- 部分失败（创建成功但提醒失败）的补偿；
- 网络抖动/超时的兜底与重试；
- 葡语输入下的意图识别准确性；
- 依赖恢复后的状态一致性。

## 6. 跨模块测试模式（可复用）

- 三态确认模式：任何写操作（创建/改期/取消）都需验证「确认成功」「用户反悔/超时」「异常中断」三态。
- 定时任务联动：预约状态变更（取消/改期）必须联动提醒任务生命周期。
- 幂等与防重：以「身份+开始时间」为唯一键，验证重复请求不产生双预约。
- 优雅降级：外部依赖（MCP/邮件/WhatsApp）故障时，返回可控话术，不暴露内部错误、不伪造成功。
- 自然语言鲁棒性：模糊/错别字/跨语种输入应追问或兜底，而非失败。
